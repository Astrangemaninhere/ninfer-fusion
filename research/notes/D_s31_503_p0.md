## 3. `/health` 载荷与脱敏（§3.5）

现状：`/health` 在 `http_server.cpp:305` 免鉴权（auth 豁免条件 `req.path == "/health"`，本补丁未动）；W16 版把 `failure.reason`（原始 `what()`）直接放进响应体。

补丁后载荷（http_server.cpp :365-398）：
```
健康: 200 {"status":"ok","engine":{"state":"ready"[,"last_request_error":{"request_id":N,"phase":"prefill","since":<epoch s>}]}}
失败: 503 {"status":"failed","engine":{"state":"failed","category":"resource"|"invariant","since":<epoch s>[,"last_request_error":…]}}
```
脱敏规则：线上只出现 `category` + request_id/phase/epoch；`reason` 一个字都不上 `/health`（自检断言 `failure.reason` 出现 0 次）。原始 reason 的两个去处：服务端日志 `[engine] engine failure class=… phase=… reason: …`（fail_all_locked 新增 :2030-2032，这是运维读原始原因的唯一入口）与 `EngineFailureState::reason`（公开 API，鉴权调用方可用）。`last_request_error` 故意跨 recover 保留（存活遥测）。
与设计的两处有意偏差：① `"recovering"` 态不实现——`recover()` 是同步调用，期间 `/health` 持续报 `failed`（编排层继续摘流，保守正确），worker 重启完成即翻 `ready`；② 设计载荷里的 `reason` 字段被 `category` 取代（脱敏的直接后果）。设计验收门 2 的"/health 报 failed + reason"据此改读为：`/health` 报 failed + category，reason 看 server log。
兼容性：健康路径仍含 `"status":"ok"`，`_e8_muse_check.sh:32` 的 `grep -q ok` 探活不变。
